# 空间化农场总览：D0 只读审计与实施方案

日期：2026-10-09。依据：`计划/产品定义与最终开发边界 v1.0.md`。审计源码：`litt1eloser/liangzihu-farm-platform`，提交 `10c2c4e`；远端 `luminous:/data/wfx/liangzihu-farm-platform` 的提交号相同。本阶段未修改仓库、数据库或部署。线上业务数据量、真实村庄与坐标尚未核实，不据此声称 T01—T15 已通过。

## 1. 结论与现有能力

| 范围 | 已有实现 | 对 P0 的结论 |
|---|---|---|
| 卫星原型 | `/map-prototype` 使用 OpenLayers、天地图影像及中文注记；`satellite_draft_points` 是账号私有草稿 | 可提取底图和交互能力；草稿必须保持私有，不转成正式设备 |
| 正式地图 | `/map` 与 `/api/v1/map` 支持授权对象、边界、设备登记位置、航次覆盖、正射、注记及搜索；界面为 SVG | 保留旧入口、图层和写入链；新总览先独立挂载，不能直接覆盖 |
| 正式对象 | `objects` 有农场、塘口、农田、渠道、设施；`saveObject` 支持新建和按版本改名，`saveBoundary` 支持草稿/审核边界及历史 | 可复用主档、ID、版本、权限和审计；缺村庄目录、对象归档入口及完整图形维护体验 |
| 设备测点 | `devices`、`points`、`device_positions` 和设备/测点页面已存在 | `devices.kind` 是物理设备/网关/摄像通道技术类型，不表示机动类别；`device_positions.created_at` 是登记时间，不能当 GPS 观测时间或实时在线 |
| 业务页面 | 对象详情、设备、测点历史、告警、任务/日历、农事、影像、地形等路由存在 | 总览只给授权概要与跳转。具体水质/养殖专页及每个业务入口的数据可用性须在 D2 逐项核实；缺失时明示不可用 |
| 权限 | `listAccessibleObjects` 按有效授权、角色和 MFA 筛选；专家还受 `resource_grants` 的资源级范围限制 | 聚合、搜索、目录与图片必须在服务端先裁剪再计数；专家不可继承普通对象总览的宽口径 |
| 响应式 | 平台外壳已有 760px 移动导航；卫星原型自有样式 | 可沿用外壳；左目录、覆盖式右抽屉、手机底部概要仍需新设计和可访问性验证 |

关键代码证据：`db/migrations/002_registry.sql`、`011_map.sql`、`044_satellite_draft_points.sql`；`src/modules/registry/{objects,devices}.ts`、`src/modules/map/service.ts`、`src/modules/field/{common,shares}.ts`、`src/modules/identity/access.ts`、`src/app/(platform)/{map,map-prototype,objects,devices}`、`src/components/platform/app-shell.tsx`。现有 `/api/v1/map` 专家分支已按边界版本和位置资源授权输出，不能简单拿普通用户查询套到专家身上。

## 2. 最小兼容设计（待审阅后编码）

### 数据库

1. 新增导航区域表 `map_regions`：UUID、所属正式 farm 对象、名称、可选可信定位点及来源、状态 active/archived、版本、创建/修改人和时间。区域不是 `objects.kind`，不产生授权继承，也不冒充行政边界。允许无几何。
2. 新增区域与正式对象的关联及变更历史。首版按“一个对象至多一个当前导航区域”建立唯一约束；未分组对象进入“未分类”。区域归档保留关联历史，当前视图将其对象放回未分类或明确显示归档筛选。跨农场关联拒绝；修改区域与对象关联时同时检查农场及对象的 `configure` 授权。若业务确认一对象可同时归多个村庄，需在迁移前调整模型，不能上线后靠重复对象实现。
3. 为设备新增极小的**业务展示分类**映射（例如固定设施/机动资产/待核），保留原 `devices.kind`、厂家来源与身份。分类必须有来源和核实标记；缺失默认为待核。任何最后位置只显示为“登记/最后已知位置”，除非另有可信观测时间与时效规则。
4. 对正式对象“归档”先明确业务影响。现有 `objects` 无归档状态，直接删除会破坏外键、历史与授权；若 P0 确认对象也需归档，增加状态与版本化审计及旧查询兼容过滤，不做硬删除。此项应在 D2 迁移前单独评审。

### API 与权限

1. 新增只读总览适配 API（暂定 `GET /api/v1/spatial-overview`），分页/视口/层级请求；从 `objects`、设备、测点、告警、工单等正式表读取。先算有效对象和资源授权，再获取明细与聚合；不能返回未授权村庄名称、数量、包围盒、图片 URL 或搜索提示。数据来源、观测时间、质量、时效、模拟、权限缺失分别表达，避免单一空值。
2. 新增区域目录的读取和维护 API（路径待实现审定）；写入使用原 `writeApi`、事务、`configure`、版本冲突、审计事件，且不允许区域赋予权限。专家总览需走单独资源级裁剪与现有专家 API 门禁；若一类概要无法保证资源粒度，返回不可用，不能放宽门禁。
3. 正式对象创建/改名继续调用 `/api/v1/objects`；边界草稿继续走 `/api/v1/map` 的版本链。新增 UI 只负责组织入口，不复制写入逻辑。数据少或无几何时目录仍可访问；定位仅依可信点或关联对象几何计算。
4. 在浏览器保留视口、选中 ID 和筛选（URL 或会话状态均可）。从业务页返回时重新请求服务器授权并验证 ID；旧状态不得绕开撤权。地图对象关联绝不依据空间邻近自动推断。

### 界面与入口

先建独立总览路由（暂定 `/farm-overview`），接入现有 AppShell；全场仅显示授权区域/对象分布，村庄层显示对象，近景按需显示设施。左侧区域目录支持搜索、折叠、未分类及无几何对象；右侧详情以覆盖式抽屉显示，默认关闭，打开和关闭均保留视口，遮挡目标时自动平移到可见范围。手机采用可关闭目录与底部概要，保证键盘焦点返回。抽屉只提供摘要和经授权验证的正式页面链接。`/map`、`/terrain`、`/map-prototype` 在 D3 验收前保持独立可用。

## 3. 分阶段实施与验收

| 阶段 | 实施内容 | 进入下一阶段的证据 |
|---|---|---|
| D0 | 本审计、方案审阅、明确真实样本与授权 | 迁移/API/权限和回滚获审阅；不改代码 |
| D1 | 独立 UI 壳、OpenLayers 底图、授权对象分布、区域目录框架、搜索、覆盖抽屉 | T01/T02/T05/T06 在离散、已授权区域验证；无几何/无权对象不泄漏 |
| D2 | 区域及关联迁移、正式对象维护入口、只读概要适配、机动分类、业务跳转 | T03/T04/T07—T10；跨角色、过期授权与直连 API 用集成测试证明 |
| D3 | 原图层与航次入口、私人点 CRUD、移动适配、故障状态、完整回归 | T01—T15；尤其 T11—T15 与原路由无退化 |

测试使用项目已有 `tests/support/db.ts` 的隔离测试库、`tests/integration/spatial-evidence.test.ts`、`registry.test.ts`、`satellite-draft-points.test.ts` 和 `tests/acceptance/phase2-experience-browser.test.ts` 作基础，再加入区域版本/归档、服务端聚合防泄漏、专家资源失效、地图返回状态、手机抽屉和断网场景。测试样本须获许可或明确标记模拟。D0 未运行会改动测试库的测试。

## 4. 回滚与发布门槛

迁移采取新增表/列、先兼容旧读取的方式；每阶段单独提交与发布。D1 新路由不改默认 `/map`；D2 新适配 API 先供新路由使用；D3 通过完整验收后才讨论入口替换。出现权限泄漏、对象历史损坏或原业务页面退化时，先撤销新导航入口并恢复上一应用版本；新增表暂留以保留已写入区域历史，不做盲目删除迁移。发布前备份数据库并验证恢复过程，核对新旧迁移版本、回滚应用与旧 API 兼容。任何生产迁移/部署都另按审阅后的实施计划执行。

## 5. 需确认的事实与审阅决策

- 提供许可使用的村庄名称、关联对象、可信中心点/边界来源；没有则按“待登记”呈现，T01/T02 不能宣称实地通过。
- 确认经营主体是否单一、一个对象是否只属于一个当前导航区域，以及区域/对象归档后在业务报表中的可见规则。
- 确认谁可维护导航区域、谁可维护正式对象；现行 `configure` 授权逐对象生效，农场父节点授权不自动覆盖子对象。
- 核实机动设备清单、业务分类依据和是否存在带观测时间的可信位置 API；现有 `device_positions` 不足以证明实时位置。
- 指定首批对象的实际业务链接（水质、养殖、农事、告警、工单等）及可用数据；不存在的专页须标为不可用。
- 核对正式环境的天地图 Key/配额、瓦片加载及不同网络下表现。原型可用不等于上线验收。

本报告是 D0 交付提案。依 v1.0 第 9、12 节，方案审阅通过后才开始 D1 编码、数据库迁移和部署。
