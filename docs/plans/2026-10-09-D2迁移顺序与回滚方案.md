# D2 数据模型与业务整合：迁移顺序与回滚方案

日期：2026-10-09。依据[冻结的产品定义](../../计划/产品定义与最终开发边界%20v1.0.md)和[D0 审阅记录](../../报告/空间化农场总览-D0只读审计与实施方案.md)。本文件是 D2 的实施门槛；各段单独提交并验证。

实施时发现运行库已有闸门准备迁移 `045_gate_deployments.sql`，D2 区域与对象归档依次使用 `046_map_regions.sql`、`047_object_archive.sql`。生产已分别执行 046 和 047，具体证据见[D2 验收记录](../acceptance/d2/2026-10-09-D2数据模型与业务整合验收记录.md)。

## 实施顺序

1. **D2-0，基线与备份**：记录生产 Git 提交、已应用迁移、Web 构建和数据库状态；取得可恢复的数据库备份。只在隔离测试库验证迁移和回退路径。
2. **D2-1，区域关系**：新增 `map_regions` 与带生效时段的 `map_region_links`，实现同一农场内村庄新增、重命名、归档、恢复、对象关联与历史查看。一个对象同时只能属于一个有效区域。服务端校验农场和对象的 `configure` 权限；目录计数只统计当前用户有权查看的对象。该阶段不修改旧 `/map`。
3. **D2-2，正式对象**：给 `objects` 增加可空归档字段，沿用对象版本与审计。提供正式地块、塘口的创建、名称维护、归档与恢复入口，并提供边界草稿入口；草稿不得自动变成已核验边界。归档只影响新总览的默认目录；旧对象主档和历史业务关系仍可读取，旧列表显式标识归档状态。不可物理删除。
4. **D2-3，总览整合**：在新 `/farm-overview` 使用授权对象及区域关系；补充轻量只读业务概要。机动设备继续使用 `devices` 身份，识别有效 `machinery_bindings` 与 `/machinery` 入口；`machinery_evidence.track` 仅作历史证据，不标为实时定位。未能确认类别的设备保持待分类。
5. **D2-4，验收与上线**：分别检查管理员、经营主体、技术员、作业人员、维保人员及专家的读写权限；检查区域和对象归档前后的历史关系、旧 `/map`、对象台账和 `/machinery`。在隔离测试库通过迁移、类型、构建和浏览器用例后，分阶段部署并保存截图。真实现场数据验收单独记录，不用合成数据替代。

迁移按编号独立提交。迁移工具会把一次运行中所有待执行 SQL 放入同一个事务，因此生产每次只发布当前阶段的迁移文件和代码。已应用 SQL 不再修改，以免校验和失配。

## 最小模型与兼容规则

- `map_regions` 仅是农场内的目录分组，不作为正式边界或独立授权资源；名称、版本、归档时间和维护来源均留痕。关联表保留起止时间、操作者和变更依据；区域归档时结束有效关联，恢复后由用户重新关联，不暗中恢复旧关联。
- 正式对象归档保留 `objects`、`object_versions`、测点、设备、农事记录和历史证据。新总览默认隐藏归档对象，管理视图可查看和恢复；旧业务读取保持兼容，写入规则不在 D2 偷换。
- 区域操作要求农场与目标对象同属一棵树，并在服务端验证 `configure`。读取必须从现有地图授权对象集合派生，专家仅看到明确授权的资源，不通过区域名称、数量或搜索泄露其他对象。
- 机动目录首先依据已有有效农机绑定确认机具和终端。设备和绑定使用原主键；历史轨迹只在相应业务入口查看。D2 不建设实时流、调度或第二套轨迹系统。

## 回滚与数据保护

每段上线前保存数据库一致性备份、迁移表清单、Git 提交号、现用 Web 构建和容器状态；在隔离环境确认备份可读取。新增表和可空列采取向前兼容方案。

- **迁移执行失败**：事务回滚后停止发布；检查 `schema_migrations` 和业务表，修复迁移后重试。
- **新页面或接口失败**：切回上一阶段 Git 提交与 Web 构建，保留新增表/列和已写入的历史记录；旧代码不依赖它们。关闭或撤销新入口，不做破坏性 down migration。
- **已写入 D2 数据**：优先修复并保留区域关联和对象版本。只有发现无法以向前修复恢复一致性，才考虑完整数据库恢复；恢复会覆盖备份后所有业务写入，须先明确影响窗口并取得用户批准。
- **旧页面异常**：立刻切回上一阶段 Web 构建，核对 `/map`、`/objects`、`/machinery` 和数据库读写；不以删除历史数据解决兼容问题。

D2 到此为止，不进入 D3 或现场设备控制。
