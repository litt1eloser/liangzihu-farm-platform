## 1. 产品定义（已确定）

**梁子湖地图是面向分散在多个村庄的农业对象的“空间化农场全景工作台”。** 它让用户快速看到农场在哪里、主要地块/塘口怎样分布、有哪些重要设施、哪里存在值得关注的变化；深入的设备监控、遥测分析、农事、告警处置和设备控制由既有业务模块承担。

| 决策 ID | 状态 | 已确定事项 | 解释及禁止偏移 |
|---|---|---|---|
| P-01 | **已确定** | 农场全局总览是默认定位 | 不是第二套物联网监控后台、指挥大屏或专业 GIS 工作站。 |
| P-02 | **已确定** | 业务对象优先 | 默认关心地块、塘口、渠道、设施和区域概况；普通设备详细遥测按需进入原业务模块。 |
| P-03 | **已确定** | 多个村庄、多个不连续空间位置 | 地图能够从全场快速定位到区域、地块、塘口及设施，不假定经营区域连成一片。 |
| P-04 | **已确定** | 首选方案 B：左侧目录 + 中央卫星地图 + 右侧详情 | 左侧区域目录可收起；地图占视觉主体；选中对象后再展开右侧详情，避免始终三栏拥挤。 |
| P-05 | **已确定** | John Deere 风格为首选视觉参考 | 清爽、专业、克制的农业运营风格；暖白/深绿做界面基底，卫星影像突出，状态色用于有语义的提示。借鉴，不复制界面。 |
| P-06 | **已确定** | 保留普通地图编辑能力，但不作为首页默认模式 | 现有点位标注继续保留；绘点/线/面、基础样式、测量仍是发展方向，明确与查看总览分开。**具体功能顺序未冻结**。 |
| P-07 | **已确定** | 地图只做空间入口，不重建业务主档 | 农业对象、设备、测点、遥测、告警、工单等继续由既有业务模块管理，地图不新建平行的“地图设备表”。 |
| P-08 | **已确定** | 村庄是导航维度，不自动成为权限和经营主体 | 村庄目录与业务归属解耦；位置缺失要标明，不假造坐标或行政边界。 |
| P-09 | **已确定** | 设备只在地图上展示概要并链接专业业务 | 简要状态/异常提示可以投影到地图；详细监控、历史曲线及控制工作流属于对应模块。 |
| P-10 | **已确定** | 不推翻现有技术栈 | 保留 Next.js + React + OpenLayers + 天地图 + PostgreSQL/PostGIS；继续兼容原有 Cesium/三维体系，不另起物联网平台。 |
| P-11 | **已确定** | 村庄/经营片区目录必须由授权用户自行维护 | 允许新增、重命名、归档和关联对象；二期新增村庄无需改源码或重新发布；目录条目不假冒官方行政区划。 |
| P-12 | **已确定** | 地块、塘口等农业对象必须可由授权用户新增和维护 | 新建对象保留真实业务 ID、对象类型、位置/边界来源及草稿/核实状态；不把 M2-A 的私人注记当作正式农业对象。 |
| P-13 | **已确定** | 机动设备从固定村庄目录独立组织 | 登记归属/停放基地与当前空间位置分开，位置缺失或过期不显示为实时定位；目录可筛选某村当前附近机动设备，但不因移动修改业务归属。 |

## 2. 当前临时假设（未冻结为事实）

| 假设 | 本轮暂用口径 | 后续核实办法 |
|---|---|---|
| 经营组织 | 暂按 **一个农场统一管理**，地块/塘口分布在多个村庄 | 向实际项目负责人确认是否存在多个经营主体/合作社；现阶段不把单主体假设写死为数据库唯一结构。 |
| 村庄归属 | 允许按已登记的村庄名称或管理区域做导航 | 核对是否已有可信村庄归属、区域名称、中心点和边界；不得以地图空间邻近自动推断经营关系。 |
| 首页摘要 | 可能显示各区域地块/塘口数量、少量关注事项 | 只有真实、当前授权、定义明确的统计才显示；缺数据就显示未知或缺资料，不能虚构“运营健康度”。 |
| 用户角色 | 农场负责人可全局浏览的交互作为设计起点 | 后续必须回到原项目的角色＋对象范围权限，不能据此推断每个人拥有全场权限。 |

## 3. 必须继承的原项目能力与约束（沿用原项目，不视为新需求）

| 原有体系 | 本轮地图与之的关系 | 不允许发生的回退 |
|---|---|---|
| **账号、权限与审计** | 复用既有对象范围、资源范围、操作权限；服务端按实际访问对象校验 | 图层开关、搜索或地图接口绕开授权；将只读视为可编辑/可控制。 |
| **农业对象主档**（`objects`） | 以业务对象 ID、可信边界和版本为事实来源 | 为显示方便另建一套与对象主档冲突的田块/塘口身份。 |
| **设备、数据源、测点**（`devices` / `data_sources` / `points`） | 根据原设备 ID 和 `device_positions` 展示位置与类型；查已有测点 | 将地图 marker、真实设备、一个传感测点视为同一概念。 |
| **遥测与接入质量**（`observations`、`point_current`、`source_health`） | 地图使用已有新鲜度、质量、来源、时间口径显示摘要 | 把厂家接口可用误写为设备在线，或把过期数据当实时状态。 |
| **告警、维护和工单** | 地图链接到既有告警、原始证据和工单页面 | 新建独立 `map_alerts` / `map_work_orders` 复制业务事实。 |
| **监控、无人机及航次资料** | 保留已有摄像头、影像、飞行记录、成果图层的入口与权限 | 用一个漂亮地图取代或删除原来的媒体/航次业务能力。 |
| **农事、生产批次、库存、溯源、科研及其他既定模块** | 地图通过对象 ID 作为上下文，后续按需展示已有的合法摘要和链接 | 将这些原模块遗漏、合并成地图表单，或假定其已有数据/接口全部上线。 |
| **二维 `/map`、三维/地形功能** | 与现有地图 API 和 Cesium/私有 3D Tiles 成果保持兼容；地图新原型不能覆盖正式模块 | 为追求 M2 原型效果破坏已有地图、三维和测绘验证链。 |
| **M2-A 草稿点位原型**（`satellite_draft_points`） | 保留已验证的中文输入、私人草稿、保存、版本冲突等行为 | 擅自把草稿点位升级为经核实的真实设备或正式经营区域。 |
| **控制记录与设备团队接口** | 可从地图查看控制申请/分层反馈，未来通过已有鉴权业务入口发起经许可的申请 | 地图直接发送厂家协议或声称控制申请等于设备已执行。真实执行适配器 G15 仍待设备资料和联合验证。 |
| **合成/真实数据隔离** | 用虚拟设备演示时在界面明确标注“模拟”，生产统计不混入演示数据 | 用演示数值冒充现场实时测量、验收或控制反馈。 |

原项目已经确认“不建展示大屏/指挥中心、不做完整数字孪生、单一系统分模块、厂家适配器接入、手机优先二维”等原则。原项目曾规划三维用于展示和地形灌排，并单独要求测绘基准与实测误差验收；**本轮聚焦二维产品界面，不代表取消那些原有三维要求**。

## 4. UI/交互基线（已确定方向，具体像素待设计）

- **默认总览**：中央是真实卫星地图；左侧是“区域目录”，优先支持搜索和选择村庄/区域、地块、塘口；右侧详情默认收起。
- **左侧目录与图层开关是两件事**：前者解决“去哪里”，后者解决“显示哪类空间数据”，可以共享面板，但数据与操作语义不得混淆。
- **对象选中**：列表与地图使用同一个选择身份；点地图对象或点列表对象，都能定位并打开概览；详细监控、农事、告警等沿已有页面继续操作，回来后尽量保留选择/视图上下文。
- **编辑行为**：编辑地图时才显示绘制、修改、删除；设备登记走既有设备主档，地图注记不自动变成设备。
- **信息密度**：广域尺度看区域分布与少量重要提示，放大后看地块/塘口与设施；不要在全场尺度密布监测数值或全部设备名称。
- **视觉规范**：浅色面板、深绿品牌色、地块与水域弱填充、细边界、语义明确的图标；告警不与类型色/选中色混淆。不先规定固定颜色值、侧栏像素、缩放阈值，先做一页真实数据场景的低保真/高保真比较。
- **移动端**：沿用原项目的手机二维优先和按权限展示；不是把桌面三栏压缩成三列。具体窄屏交互待验收。

## 6. 当前版本的明确非目标（拒绝范围膨胀）

本轮不重新开发设备监控中心、实时遥测平台、控制引擎、告警引擎、农事管理系统；不建设大屏/指挥中心、数字孪生总控台、专业 GIS 全功能编辑器、插件商城、任意设备协议设计器、复杂轨迹平台、3D 编辑器或无人机自动任务规划。也不为了 UI 效果把系统既有权限、数据质量和测绘证据降级。

**暂缓本轮 ≠ 永久删除原项目需求。** 如果功能属于导师原计划的其他阶段，仍按原计划保留；这里只冻结“当前地图 UI/空间运营集成”这一轮的范围。

## 8. 可直接继承的结论（一句话）

> **用 John Deere 风格的清爽卫星地图工作台展示分散村庄的农业生产对象；地图负责总览、搜索、定位、概要和跨模块入口，所有真实设备/农业业务仍以既有主档及有证据的数据为准，设备控制与专业监测由原系统和专业团队承担。**

## 9. v0.2 补充决定：目录可扩展与机动设备（2026-10-09）

### 9.1 村庄/区域是用户维护的导航分组，而不是代码里的固定名单（已确定）

- 农场业务当前**暂按单一主体经营**，但这是待实地核实的临时假设，不写死为唯一租户或权限结构。
- 具备相应配置权限的用户可新增、编辑名称、调整关联、归档村庄或经营片区；日后工程扩展、新增村庄时不必修改前端枚举或源码。
- 村庄名称首先是用户定义的**经营区域导航索引**。它可能对应实际行政村，但不能未经核实把名称、中心点或边界当作官方行政区划数据；允许仅有名称而暂缺可信几何。
- 某村下暂时没有已登记地块时，目录仍可显示“尚无对象”；没有可信坐标或边界的对象继续在列表中显示“位置待登记”，不能伪造地图点。
- 工程期次（一期/二期）若未来确需统计，应与区域身份区分；不能把“二期新开放”直接当作另一种村庄类型或权限规则。

### 9.2 地块/塘口能增、改、归档，但继续复用正式对象主档（已确定）

- 有权限的用户可以创建地块、塘口等对象，录入名称、对应村庄或经营片区，并按业务需要绘制/维护地理位置或边界。
- 普通新增对象允许先保存草稿，边界的权威性仍依照原项目 `objects` / `boundary_versions` 等既有的来源、版本、核实与权限规则处理；未核实边界不得冒充权威测绘成果。
- 原项目 `objects.kind` 当前枚举 `farm / pond / field / channel / facility`，没有 `village`；**不预设**可直接将村庄插入 `objects`，也不预设已经有“区域管理”接口。后续实施前应审计现有对象建档 API、权限与可兼容迁移方式，再决定区域分组的存储方案。
- 地图上的“私人注记”与正式地块/塘口记录是不同性质，不能用创建点位的 API 偷换正式业务主档。

### 9.3 机动设备的导航与位置事实（设计建议，等待确认）

- 左侧区域目录保留“村庄 → 地块/塘口/固定设施”；另设独立的**机动设备**入口，展示无人机、收割机、拖拉机等经实际登记的移动对象。不必把移动设备永久塞进当前所在村庄。
- 机动设备至少区分三种概念：`登记归属或停放基地`、`最近已知位置`、`实时有效位置`。归属不随位置更新而变化，跨村作业只影响当前位置/地图展示。
- 在村庄视图可以按可信当前位置展示“当前在附近的机动设备”，但该项是动态筛选，不是永久归属迁移；仅靠空间接近不得自动改变负责人/经营主体或服务关系。
- 当前 `device_positions` 是**版本化设备位置**，不应直接当作连续 GPS 轨迹。没有实时定位集成时，只能展示经注明时间与来源的“登记位置”或“最后已知位置”，或者“位置未知”；不伪造实时位置。
- 地图显示状态仍由现有业务适配器输出摘要；详细遥测/任务/设备控制在其他既有模块内完成。移动设备的具体定位频率、路线和历史轨迹需求不在本版本冻结范围。

### 9.4 目录概念结构（机动设备部分待确认）

```text
全部农场
├─ 区域目录（用户动态新增）
│  ├─ 村庄 A
│  │  ├─ 地块
│  │  ├─ 塘口
│  │  └─ 固定设施
│  ├─ 村庄 B
│  └─ 新增村庄（有权限用户）
├─ 机动设备（独立入口，已确认）
└─ 未归类 / 位置待登记
```

上述结构为产品导航概念，而不是数据库外键层级。左侧目录的数据和图层显隐仍需分开处理，实际查询由现有服务端授权决定。

## 10. v0.3 决策更新：第一至第三项已锁定，第四项进入讨论（2026-10-09）

### 10.1 第一项：区域目录（已锁定）

- 全场 → 用户自定义村庄/经营片区 → 地块、塘口、固定设施；机动设备从独立入口进入，未归类/位置待登记单列。
- 村庄属于导航分组，不默认是正式行政区或权限单元；先按统一农场经营假设设计，但不写死未来经营主体关系。
- 授权用户能增改村庄和地块/塘口；农业对象使用既有 `objects` 的 ID 与版本、边界来源及授权约束。
- 当前 `objects.kind` 不包含 `village`，真正实现动态村庄前，须设计可维护的分组数据模型；不得把村庄名称固定在 React 枚举中。

### 10.2 第二项：全场默认显示规则（已锁定）

- 使用“方案 B”：**全场看农业分布，放大看固定设施，点开看状态概要**；全场主要呈现村庄/片区、农田与塘口总体分布及少量有依据的关注事项。
- 缩放到区域后才渐进显示地块/塘口边界与名称、渠道、水闸、水泵等重要固定设施；普通摄像头和传感器默认不挤满全场地图。
- 机动设备通过独立目录快速查找；航拍覆盖、正射、注记等保留为按需显示的原有图层，不能因为新 UI 被删除。
- 村庄目录负责“去哪里”，图层开关负责“显示什么”。清爽的 John Deere 农业运营视觉风格继续作为首选。
- 首页少量摘要只在有真实、当前授权且定义清楚的数据时显示；演示数字必须显著标记为模拟。

### 10.3 第三项：右侧详情与编辑边界（已锁定）

- 采用“方案 A”：右侧面板默认关闭；点击地块、塘口、固定设施或普通注记后开启统一布局的对象概要；关闭不改变地图位置。
- 概要包括名称、类型、区域/归属、地理资料的可信状态，以及少量当前可用的生产或监测摘要、关注事项和业务入口。缺数据必须显示缺失或待核实，不能显示虚构的正常状态。
- 农田/塘口/真实设备的正式资料修改、农事记录、水质监测详情、告警/工单处理、控制申请等均**跳转现有有权限的业务页面**，禁止在地图里复制专业业务表单与控制逻辑。
- 唯一常规例外：**普通地图注记**可在地图编辑模式直接修改名称、说明和基础表现形式，继续与真实物理资产和主档区分。
- 示例塘口操作链：选中塘口 → 右侧显示品种/批次与关键水质和异常概要（以可用事实为准）→ 进入已有测点历史、农业业务、告警或工单 → 返回地图保留选中对象与视口（应尽量实现）。

### 10.4 第四项：与现有项目的数据对接（**2026-10-09 已锁定方案 B 的原则；细节待技术审计**）

**2026-10-09 对当前开发仓库的只读核查：**

| 当前已有的真实数据来源 | 可直接复用的事实 | 当前缺口/注意事项 |
|---|---|---|
| `GET /api/v1/map`、`src/modules/map/service.ts` | 已按既有授权返回对象边界、设备位置、航次覆盖、正射预览和注记等；边界和位置有来源与版本 | 不是直接可用的“农场总览状态 API”；`bbox` 查询边界时无几何的对象不能仅靠空间查询找回；与区域目录查询应分离 |
| `GET /api/v1/objects` 与 `src/modules/registry/objects.ts` | 对象主档可按已有范围读取、新增、改名称；类型为 farm/pond/field/channel/facility | 没有村庄分组模型；新增“村庄”不能用前端硬编码，也不能未经设计直接改 kind 约束 |
| `devices`、`device_positions`、`GET /api/v1/devices` | 设备 ID、业务对象关系、来源、型号、版本化位置可复用 | `devices.kind` 仅为 physical/gateway/camera_channel，**不等于**水闸/无人机/收割机等业务展示类别；`device_positions` 不是实时轨迹库 |
| `points`、`point_current`、`source_health`、`src/modules/telemetry/queries.ts` | 已有测点、最新有效值、历史和来源质量语义 | 地图概要所需的“少量指标摘要”仍需在授权服务端正确关联、压缩；不可从传感点自行推断“设备整体正常” |
| `/api/v1/alerts`、`/api/v1/work-orders` | 已有告警/工单业务记录和入口 | 地图需要**按当前授权对象汇总**关注事项，而不是新建 map_alerts/map_work_orders |
| `/map`、`/map-prototype` 与 `/api/v1/map-prototype/points` | 正式地图已有功能，卫星 OpenLayers 原型提供中文标注和草稿持久化 | 现有正式 `/map` 与卫星原型是两个实现入口；需整合/逐步迁移并做回归，不能简单删除任何一端 |

**已确认的最小集成原则（方案 B）：**

1. 浏览器中的 OpenLayers 负责底图、地理图形、图标、缩放与选中状态，不直接查询数据库或厂家接口。
2. 复用 `/api/v1/map` 的正式空间数据和已有 `/objects`、`/devices`、`/points`、`/alerts`、`/work-orders` 等业务服务；根据性能和权限需要补一层**只读、经授权的总览聚合/呈现适配接口**，避免让页面自行拼装大量业务事实。
3. **只对真正缺失的村庄动态分组和必要的设备显示类别做最小兼容扩展**；表/字段/API 方案须在技术设计阶段进一步审计确定，不能提前承诺零迁移或直接修改正式业务枚举。
4. 用户的普通标注依然是独立的草稿或正式注记，不因为显示在同一张图上就升级为真实农场对象。
5. 正式 `/map`、`/terrain` 及既有监控、航次、设备、权限和控制页面保持可用；新 UI 可分阶段验证、集成，而非先替换后补功能。
6. 模拟设备/模拟测值需要从 API 到界面明确标记；实时更新不可靠时显示原采样时间/来源，通过可信快照恢复，不假装设备一定在线。

**第四项已拍板的架构方向（2026-10-09）：**采用“基于正式业务接口的只读聚合/呈现适配层，逐步整合卫星 OpenLayers 工作台”，而非新建平行业务表或直接替换正式 `/map`；详细接口字段、动态目录存储和迁移计划留待技术设计。

## 11. v0.4 决策更新：第四项锁定，第五项 UI 原型进入讨论（2026-10-09）

### 11.1 第四项：接入既有项目（已锁定）

- **确定采用方案 B**：保留对象、设备、遥测、告警、工单、航次及二维/三维现有业务模块，在当前 Next.js 系统内增加最小、受权限保护的只读总览展示适配层；浏览器不直接拼装厂家接口，也不复制正式设备台账和状态事实。
- 区域目录可以增删改归档，但数据库结构、迁移位置、接口字段与性能策略待实施前代码审计确定；业务类型与技术类型不同，必要时只做最小兼容扩展。
- 新卫星 OpenLayers 工作台不能破坏既有 `/map`、`/map-prototype`、`/terrain`、原业务页面、权限、来源/核实状态或中文点位 CRUD 行为。
- 实时数据与模拟数据保持来源和时间标识；默认只聚合可信、当前可授权的数据，任何“正常”状态不得凭无数据推断。

### 11.2 第五项：UI 页面与交互原型（待用户最终确认的建议，**未锁定**）

**视觉语言（已有方向）**：以 John Deere Operations Center 的简洁农业运营界面为参考，搭配保守的暖白/深绿界面和清晰的卫星影像主体；地图对象、图层、关注事项的颜色应有不同语义，不能只靠颜色区分。适度使用农业绿、水域蓝、告警橙/红；不把页面改成深色指挥大屏。

**桌面初版页面结构（拟）**：
1. 复用原平台主导航。地图页顶部只保留位置层级/标题和紧凑操作（全场复位、图层、进入编辑模式、可达的三维入口），避免复杂工具条。
2. 左侧固定可收起的“区域目录”，包含搜索、全部农场、自定义村庄/片区、村庄下地块/塘口/固定设施、机动设备、未归类/位置待登记；图层显隐逻辑与目录逻辑独立。
3. 中间天地图卫星影像 + OpenLayers：全场显示村庄/农业分布和有依据的关注提示，放大逐步出现地块/塘口、重要固定设施；默认不显示全量设备实时数值；缺位置的实体只进入列表，不虚构几何。
4. 右侧概要默认关闭。选中地块、塘口、设施、移动设备或注记时打开；标题/类型/区域、资料可信度、少量已授权可信事实、关联业务入口；普通标注仅在编辑模式做直接修改。地图关闭详情后不重新定位。
5. 正式资料编辑、遥测曲线、农事、告警与工单处置、控制申请均跳已有权限校验的业务入口；返回地图保留视口、对象选中和筛选状态（具体状态保存手段留待技术实现）。

**移动端初版页面结构（拟）**：保留二维地图；区域目录用抽屉/列表打开、对象详情用底部面板；不能简单压缩桌面三栏；继续沿用原项目的账号、授权和移动端规则。具体尺寸断点不在产品基线中提前锁死。

**交互流程（建议按这一条做一套完整原型）**：
- 进入地图 → 查看多村庄全场分布 → 左侧搜索/选择一个村庄 → 聚焦村庄内的塘口/地块 → 点击实体 → 右侧概要显示来源和关键业务入口 → 打开既有业务页 → 返回仍能找到原选择。
- 有编辑权限者：区域目录新增一个村庄 → 在村庄下登记地块/塘口并保存未核实边界草稿 → 地图和目录正确反映新对象；无权限用户看不到/无法执行编辑操作。
- 点击普通个人注记：查看后进入“编辑地图”模式修改；不能用注记替代真实设备/地块主档。

**最小验收清单（建议）**：

| 验收场景 | 预期结果 |
|---|---|
| A. 多村庄、不连续空间分布 | 全场视图可到达各授权经营区域；左侧导航可逐个聚焦，未登记真实区域边界时不画假行政区划。 |
| B. 动态村庄和地块 | 授权用户新建村庄及对象，不需要改前端固定列表或重新发布；无可信位置对象仍能列表查到。 |
| C. 全场→区域→对象→详情 | 点击农业对象打开适配的概要，并能跳到存在且获授权的专业业务页面；返回保留地图上下文。 |
| D. 信息密度 | 全场尺度不铺开所有设备；区域尺度逐渐展开固定设施；图层开关不改变数据权限或几何事实。 |
| E. 真实与模拟、旧数据 | 虚拟数据显著标记；监测缺测/过期/无效与离线、真实告警分离；不出现虚假的“正常率”。 |
| F. 权限与缺省情况 | 权限不同者仅见授权内容；缺边界、缺归属、位置未知、业务入口不可用有清楚提示，不能凭地理邻近或预置假的点位补全。 |
| G. 已有业务回归 | 正式 `/map`、`/map-prototype` 中文输入和 CRUD、对象页、设备/测点、航次影像、原告警工单、`/terrain` 与接口授权仍正常。 |
| H. 桌面与移动端 | 常见桌面和手机宽度可读、可操作；移动端使用列表/抽屉/底部概要，不遮蔽主要地图操作；具体基准设备在实现计划中约定。 |

**本版本不自动增加的新功能**：复杂 GIS 分析、任意用户编程的设备字段/规则系统、全量实时 GPS 轨迹、自动风险判定、3D 业务重写、专业监控大屏和原始厂家设备指令下发。它们若在导师既有计划中，则仍属原计划相应阶段，而非这轮 UI 决策的新增交付。

**尚待用户确认的界面取舍（不扩大功能范围）**：桌面右侧概要采用贴右的抽屉式覆盖地图，还是作为固定第三栏压缩地图？推荐贴右抽屉，因其在关闭后立即恢复广域地图视觉，同时需保证选中地图对象不会被遮挡。确认该点以及总体 UI 原型范围后，Q5 可锁定并形成 v1.0 产品定义。
